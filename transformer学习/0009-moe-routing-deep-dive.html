MoE 通常不替换 Attention，而是把一个 FFN 换成多个 FFN

一位“专家”内部是什么？

class Expert(nn.Module):
    def __init__(self, dim):
        super().__init__()
        self.net = nn.Sequential(
            nn.Linear(dim, 4 * dim),  # [*, C] → [*, 4C]
            nn.GELU(),                # 非线性
            nn.Linear(4 * dim, dim),  # [*, 4C] → [*, C]
        )

    def forward(self, x):
        return self.net(x)

它不是一个完整聊天模型，也不是人工预先命名的“数学教授”。多位专家结构可以相同，但参数各自独立。训练可能形成某种分工，也可能只表现出句法或位置偏好；负载均衡保证的是使用机会，不是语义专长。

具体例子句子“我 用 Python 写 循环”经过 Attention 后，每个 token 已带有上下文。MoE 会对“我”“Python”“写”“循环”的 hidden state 分别路由；四个 token 可以选不同专家，同一个 token 在下一层也可以改选其他专家。
常见误解：MoE 就是模型集成普通 ensemble 往往让多个完整模型都计算，再平均最终预测；稀疏 MoE 是一个模型内部的条件计算层，通常只执行被路由到的少数 FFN 子网。

第 2 关 · 数据流

从 [B,T,C] 到专家，再原样回到 [B,T,C]

先不要背公式。按顺序点击六步，始终问三个问题：现在一行代表谁？最后一维代表什么？下一步为什么能接上？

z = Wrx  →  p = softmax(z)  →  S = TopK(p)  →  y = Σi∈S wiEi(x)z 是 router logits；p 是专家维的路由概率/权重；S 是离散专家索引；w 是最终混合权重。

离散的部分

TopK 产生专家索引。索引跳变，不能像普通连续函数那样直接求导。

连续的部分

被选中的 gate 权重、专家 FFN、主损失和辅助概率项仍可传梯度；所以“Top-K 不可微”不等于 router 完全不能训练。

即时反馈

两种写法不要混为一个定义“先全 softmax、取 Top-K、再把入选概率除以它们的和”在数值上等于“把未入选 logits 设为 −∞ 后 softmax”。但 Switch top-1 保留全 softmax 的最高概率，不把唯一权重强制变成 1。
logit 不是“专家答对概率”它只是线性 router 给出的相对打分；softmax 也只是把这些分数归一化。模型最终是否答对由完整网络和任务 loss 决定。

深入想一层：为什么 Top-1 内重归一化会有梯度陷阱？

只有一个入选 logit 时，selected-softmax 永远等于 1；把该权重乘专家输出，主任务对这条权重路径的导数为 0。argmax 索引本身又离散。Switch-style 保留全 softmax 的 p_top1，并加入经平均概率 P 回传的负载辅助项。

为什么需要 expert capacity？

分布式系统喜欢固定形状的批量计算。Switch top-1 的经典容量近似为：

C = ceil((本批 token 数 T / 专家数 E) × capacity factor)CF > 1 留缓冲，减少 overflow；代价是更多空槽位、内存、计算与通信。一般 Top-K 的容量定义会随实现变化。

Switch 负载均衡损失到底在算什么？

Lbalance = α · E · Σi=1…E fiPifᵢ：硬分派给专家 i 的 token 比例；Pᵢ：该批 token 对专家 i 的平均 softmax 概率。f 不可微，梯度可经 P 回到 router。均匀时无系数分数 EΣfP=1。

它不是要求每个很小的 batch 机械地绝对平均，而是在训练尺度上惩罚持续拥堵。系数 α 太小可能压不住塌缩；太大又可能干扰主任务。Switch 论文使用 0.01 是那组实验的选择，不是宇宙常数。

第 5 关 · 梯度与稳定性

Balance loss 管“大家有没有活干”，z-loss 管“router 数字别爆”

Ltotal = Ltask + cBLbalance + czLz三项职责不同：完成任务、分配流量、约束 router 数值尺度。

负载均衡损失

抑制 router 长期把 token 都送给少数专家，减少死专家、硬件闲置和容量溢出。

不保证：专家一定语义多样。

Router z-loss

mean(logsumexp(logits)²) 抑制过大的 log-partition，提高指数运算的数值稳定性。

不负责：均匀分配专家。

把公式落到 moe_router_demo.py

点击步骤，左侧会高亮对应代码，右侧同时解释 Python 写法与张量形状。完整可运行文件：code/moe_router_demo.py。

class Expert(nn.Module):
    def __init__(self, dim):
        super().__init__()
        self.net = nn.Sequential(
            nn.Linear(dim, 4 * dim), nn.GELU(),
            nn.Linear(4 * dim, dim))
    def forward(self, x):
        return self.net(x)

class ToyMoE(nn.Module):
    def __init__(self, dim=8, n_experts=4, top_k=2):
        super().__init__()
        self.top_k = top_k
        self.router = nn.Linear(dim, n_experts, bias=False)
        self.experts = nn.ModuleList(
            [Expert(dim) for _ in range(n_experts)])

    def forward(self, x):              # x [B,T,C]
        flat = x.reshape(-1, x.size(-1)) # [N,C]
        logits = self.router(flat)       # [N,E]
        probs = F.softmax(logits, dim=-1)
        weights, ids = probs.topk(self.top_k, dim=-1)
        weights = weights / weights.sum(-1, keepdim=True)
        output = torch.zeros_like(flat)
        for expert_id, expert in enumerate(self.experts):
            selected = (ids == expert_id).any(dim=-1)
            if selected.any():
                weight = (weights[selected]
                    * (ids[selected] == expert_id)).sum(-1)
                output[selected] += (
                    expert(flat[selected]) * weight.unsqueeze(-1))
        return output.view_as(x), probs, ids
这段代码故意清楚，不代表生产高效逐专家 Python 循环、布尔索引和不等长小矩阵会浪费 GPU；它也没有 expert capacity、all-to-all、router float32、可微负载辅助项或 z-loss。现有脚本末尾的 bincount 方差只是教学指标，不能直接当可微训练损失。
运行方式先进入课程根目录，再运行 python code\moe_router_demo.py。输出会显示 [2,3,8] 的形状、6 个 token 的 Top-2 专家与教学版负载指标。若报错，先确认当前 Python 环境已安装 PyTorch。

代码填空：为什么专家必须放在 nn.ModuleList，不能只用普通 list？

普通 list 可以让 forward 遍历，但 PyTorch 不会把其中模块可靠地注册为子模块。结果是参数可能不出现在 model.parameters() 中，也不会自动随 .to(device) 移动或被 optimizer 更新。nn.ModuleList 同时保留列表式访问与模块注册。

第 7 关 · 从玩具代码到真实系统

真正困难的不只算法，还有搬 token、填容量与跑大矩阵

若专家分布在不同 GPU，通常不是每一步搬动专家权重，而是搬动 token activation：

本地路由算目标 expert ID
第 1 次 all-to-all把 token 发到专家所在设备
Grouped FFN专家批量计算
第 2 次 all-to-all把结果送回原设备
恢复顺序按 gate 加权合并
MoE 不保证墙钟时间更快固定 K 时，增加 E 不让专家 FFN 主 FLOPs 同比增长；但权重驻留、router 打分、token packing、负载不均、网络延迟和小 batch 利用率都可能成为瓶颈。尤其单 token 解码时，“算得少”不自动等于“响应更快”。

PDF 中代表模型应该怎样分类

算法 + 自动分片 · 2020

GShard

Transformer 中的稀疏 Top-2 gate 与自动 sharding。第二专家不是“从所有剩余专家随机抽一个”：它仍是 second-best，训练时只随机决定是否 dispatch。

路由简化 · 2021/2022

Switch Transformer

每个 token 选一位专家，降低 router、容量与通信复杂度。论文的 4× 是特定 Switch-C 对 T5-XXL 的实验结果，不是 Top-1 对 Top-2 的通用倍数。

开源模型 · 2024

Mixtral 8×7B

每个 MoE 层有 8 个 FFN，逐 token 选 2 个。官方报告约 47B 总参数、约 13B active，而不是简单的 8×7=56B。

系统 · 2022

DeepSpeed-MoE / Tutel

重点是大规模训练、推理、并行与通信优化。论文中的倍数依赖硬件、规模、基线和工作负载，不应当成任意模型的承诺。

Dropless 系统 · 2022

MegaBlocks

用块稀疏计算处理不均匀 token 数，说明“固定容量后丢 token”不是唯一实现。PDF 的“数量级提升”表述过强。

稳定训练 · 2022

ST-MoE

系统研究稳定与迁移，提出 router z-loss。它与 Switch 的负载损失解决不同问题。

第 8 关 · 检索练习与迁移

先答再看：能解释“为什么”，才算真正理解

误区：8 个专家就做 8 倍 FFN

固定 Top-2 时，专家主计算约两份；但路由与通信仍有开销。

误区：稀疏激活自动节省显存

全部专家权重仍要存放；需要分片、卸载或量化降低单设备驻留。

误区：未选专家完全没有梯度

它只没有这条 token 的主任务梯度，仍可从其他 token 获得更新。

误区：专家自然分成数学与代码

专业化可能涌现，却不保证可解释；均衡使用也不等于语义多样。

误区：dropped token 从句子消失

经典固定容量实现只跳过本次 expert 计算，残差仍保留表示。

误区：Top-K 不可微所以 router 不学

索引离散，但选中权重、概率代理与辅助损失仍能向 router 传梯度。

迁移题：负载完全平均是否一定最好？

不一定。硬件希望负载接近均匀，但任务数据可能确实需要非均匀专业化；过强的平衡系数会与主任务冲突。目标是避免持续拥堵、闲置与溢出，同时保留有用的条件计算，而不是强迫每个小 batch 精确平均。

迁移题：怎样判断一个“MoE 更快 4×”的说法是否可信？

至少追问：和哪个 dense/MoE 基线比？质量是否相当？是达到固定质量的训练时间、单步吞吐还是推理延迟？使用什么硬件、batch、序列长度、精度、专家并行与容量因子？Switch 论文的 4× 就是特定 Switch-C 对 T5-XXL 的固定实验，而非通用常数。

一手资料与继续学习

  • Shazeer et al. (2017), Sparsely-Gated MoE — 原始 noisy Top-K、importance/load losses；实验架构基于 LSTM，不是 Transformer 论文。
  • GShard (2020) — Transformer Top-2 gate、容量与自动分片。
  • Switch Transformer (2022 JMLR) — Top-1、容量、dropped token、可微负载代理；本课主参考。
  • ST-MoE (2022) — router z-loss 与稳定、可迁移的稀疏模型。
  • Mixtral of Experts (2024) — 8 个 FFN、每 token 选 2 个，以及 total/active 参数边界。
  • DeepSpeed-MoE、Tutel、MegaBlocks — 从算法走向系统、通信和 dropless 计算。
  • PyTorch ModuleList、torch.topk、F.softmax — 课程代码对应的官方 API。
  • PaLM 2 Technical Report — 用于核对原 PDF 将 PaLM 2 归为 MoE 的说法；报告没有给出该架构归类。
